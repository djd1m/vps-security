# tmux: установка и сессии, которые возвращаются после перезагрузки

Дата: 2026-09-13. Платформа: Ubuntu 22.04 / 24.04.

Дополняет [`install-tmux.sh`](install-tmux.sh) из этого репозитория, который
ставит tmux, пишет `~/.tmux.conf` и по желанию добавляет автоподключение при
SSH-входе. Тот скрипт закрывает **обрыв SSH**. Этот документ закрывает
**перезагрузку сервера** — случай, который скрипт не закрывает и закрыть не может.

---

## Главное, что нужно понять до установки

**Сессия tmux не переживает перезагрузку. Это не настраивается.**

Сессии живут внутри процесса `tmux: server`. При `reboot` система убивает все
процессы — вместе с сервером исчезают все сессии и всё, что в них работало:
компиляция, `apt upgrade`, Claude Code, Codex. Плагины вроде `tmux-resurrect`
восстанавливают *раскладку* окон и панелей, а не состояние работавших программ.

Что tmux действительно даёт и что из этого чем обеспечивается:

| Событие | Сессия выживает? | Чем обеспечивается |
|---|---|---|
| Обрыв Wi-Fi, закрытый ноутбук, таймаут SSH | Да | Поведение tmux по умолчанию, настройка не нужна |
| Осознанный `exit` из последней сессии пользователя | Да, если `KillUserProcesses=no` | Значение по умолчанию в Ubuntu; `enable-linger` даёт гарантию |
| Перезапуск `sshd` | Да | tmux не является потомком `sshd` |
| `systemctl restart user@<uid>.service` | Нет | Сервер tmux лежит в cgroup пользовательского менеджера |
| **Перезагрузка сервера** | **Нет** | Ничем. Сессию можно только пересоздать при загрузке |

Поэтому цель раздела 3 — не «сохранить сессию», а «после загрузки сервера сессия
`main` снова существует, и `tmux attach -t main` сразу работает». Что было внутри
до перезагрузки — не возвращается, и рассчитывать на это нельзя.

## 1. Проверка до установки (ничего не меняет)

```bash
. /etc/os-release && echo "$PRETTY_NAME"
command -v tmux && tmux -V || echo "tmux не установлен"
apt-cache policy tmux | head -3
id -u
loginctl show-user "$USER" -p Linger
grep -rn '^\s*KillUserProcesses' /etc/systemd/logind.conf /etc/systemd/logind.conf.d/ 2>/dev/null \
  || echo "KillUserProcesses не переопределён (по умолчанию no)"
systemctl --user show-environment >/dev/null 2>&1 && echo "systemd --user доступен" \
  || echo "systemd --user НЕДОСТУПЕН — раздел 3 не сработает"
```

**Ожидается:** Ubuntu 22.04 или 24.04; `tmux` либо отсутствует, либо версии 3.2+
(в 24.04 штатная — 3.4); `systemd --user доступен`.

**STOP**, если `systemd --user` недоступен (контейнер без systemd, урезанный
образ): автозапуск из раздела 3 работать не будет, а `nohup`/`@reboot` в cron
вместо него — путь к бесконтрольным процессам, отдельный разговор.

**STOP**, если `KillUserProcesses=yes`: сессии будут умирать при выходе из
последнего SSH-логина, и `enable-linger` в разделе 3 становится не «на всякий
случай», а обязательным условием.

## 2. Установка

```bash
sudo apt-get update -qq
sudo DEBIAN_FRONTEND=noninteractive apt-get install -y -qq tmux
tmux -V
```

**Ожидается:** `tmux 3.4` на 24.04, `tmux 3.2a` на 22.04.

Ставим **штатный пакет из архива дистрибутива**, не PPA и не сборку из
исходников. Причина прикладная: политика безопасности на этих хостах —
`unattended-upgrades` в режиме security-only, она обновляет пакеты из
`${distro_id}:${distro_codename}-security`. Пакет из стороннего репозитория в эту
политику не попадёт, и его дыры придётся закрывать руками. Версии 3.2+ достаточно
для всего, что используется ниже.

Проверка, что пакет именно из архива:

```bash
apt-cache policy tmux | sed -n '1,6p'
```

**Ожидается:** строка `500 http://archive.ubuntu.com/ubuntu <codename>-updates/main`
или `-security/main`, а не сторонний хост.

## 3. Сессия, которая возвращается после перезагрузки

Механизм: пользовательский systemd-юнит создаёт сессию при загрузке, а
`enable-linger` разрешает пользовательскому менеджеру стартовать до и жить без
интерактивного входа. Без linger юнит запустится только при первом SSH-логине —
то есть ровно тогда, когда он уже не нужен.

### 3.1 Linger

```bash
sudo loginctl enable-linger "$USER"
loginctl show-user "$USER" -p Linger
```

**Ожидается:** `Linger=yes`.

Что это меняет: пользовательский менеджер (`user@<uid>.service`) стартует при
загрузке системы и не останавливается после выхода из последней сессии. Новых
прав это не выдаёт — менеджер и так работает под этим же пользователем.

### 3.2 Юнит

```bash
mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/tmux-main.service <<'UNIT'
[Unit]
Description=tmux session "main"
Documentation=man:tmux(1)
After=default.target

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/tmux new-session -A -d -s main
ExecStop=/usr/bin/tmux kill-session -t main
ExecReload=/usr/bin/tmux source-file %h/.tmux.conf

[Install]
WantedBy=default.target
UNIT
systemctl --user daemon-reload
systemctl --user enable --now tmux-main.service
systemctl --user is-active tmux-main.service
tmux ls
```

**Ожидается:** `active`, и в `tmux ls` строка вида
`main: 1 windows (created …)`.

Почему юнит написан именно так:

- `new-session -A -d -s main` — `-A` означает «подключиться, если сессия есть,
  иначе создать». Юнит идемпотентен: повторный `start` при живой сессии не
  падает с `duplicate session`. Без `-A` вторая попытка возвращает ошибку и юнит
  считается сломанным.
- `Type=oneshot` + `RemainAfterExit=yes` — команда завершается сразу (сервер tmux
  демонизируется сам), но юнит остаётся `active`, и systemd не убирает cgroup с
  живым сервером. `Type=forking` здесь хуже: если сервер tmux уже поднят другой
  сессией, `new-session` не форкает нового демона и systemd не находит главный
  процесс.
- `KillMode=none`, который встречается в рецептах из интернета, не используется:
  в systemd 255 (Ubuntu 24.04) он объявлен устаревшим и пишет предупреждение в
  журнал. Штатной остановки юнита достаточно.
- `After=default.target`, а не `network-online.target`: сессии сеть не нужна.

### 3.3 Проверка настоящей перезагрузкой

Это единственная проверка, которая что-то доказывает. Она **мутирующая** —
выполняйте, когда перезагрузка хоста допустима, и предупредите тех, кто им
пользуется.

```bash
tmux new-session -d -s main \; send-keys -t main 'date -u > /tmp/tmux-reboot-probe' C-m
sudo reboot
```

После загрузки, в новой SSH-сессии:

```bash
uptime -p
systemctl --user is-active tmux-main.service
tmux ls
tmux attach -t main
```

**Ожидается:** аптайм — минуты; юнит `active`; `tmux ls` показывает `main`;
`attach` открывает **чистую** оболочку. Файл `/tmp/tmux-reboot-probe` при этом
существует — это доказательство, что до перезагрузки в сессии действительно
что-то работало и что новое окно — новое, а не «сохранённое».

Если `tmux ls` отвечает `no server running` — почти всегда не включён linger
(`loginctl show-user "$USER" -p Linger`) или юнит не заенейблен
(`systemctl --user is-enabled tmux-main.service`).

## 4. Конфигурация (опционально, но перед агентскими TUI — обязательно)

`install-tmux.sh` из `vps-security` пишет готовый `~/.tmux.conf`: префикс
`Ctrl+A`, мышь, vi-навигация, разделение панелей на `|` и `-`, статус-бар. Он
делает бэкап старого конфига. Если tmux используется как окно для TUI Claude Code
или Codex, важны три строки из него и одна оговорка:

```tmux
set -sg escape-time 10        # иначе Esc в TUI распознаётся с задержкой
set -g history-limit 100000   # чтобы длинный вывод не терялся из буфера
set -g default-terminal "tmux-256color"
```

Оговорка про `set -g mouse on`: мышь удобна для переключения панелей, но
перехватывает выделение — копирование мышью начинает работать иначе (с Shift),
и часть TUI получает события прокрутки вместо терминала. Если tmux нужен в
первую очередь как обёртка для агентских сессий, мышь лучше не включать.

## 5. Автоподключение при SSH-входе (опционально)

```bash
cat >> ~/.bashrc <<'BLOCK'

# tmux-autostart
if [ -n "$SSH_CONNECTION" ] && [ -z "$TMUX" ] && command -v tmux >/dev/null; then
  tmux attach -t main 2>/dev/null || tmux new -s main
fi
BLOCK
```

Ровно этот блок добавляет `install-tmux.sh`. Осознайте риск до применения: любая
ошибка в `~/.tmux.conf` после этого ломает **каждый** интерактивный SSH-вход.
Держите вторую SSH-сессию открытой при первом входе после правки — то же правило,
что и для хардининга sshd.

Безопаснее не трогать `.bashrc` и завести алиас:

```bash
echo "alias m='tmux new-session -A -s main'" >> ~/.bashrc
```

## 6. Приёмка

| Код | Проверка | Ожидается |
|---|---|---|
| T-1 | `tmux -V` | 3.2+ |
| T-2 | `apt-cache policy tmux` | источник — архив дистрибутива |
| T-3 | `loginctl show-user "$USER" -p Linger` | `Linger=yes` |
| T-4 | `systemctl --user is-enabled tmux-main.service` | `enabled` |
| T-5 | `systemctl --user restart tmux-main.service; tmux ls` | сессия `main` на месте, юнит `active` (идемпотентность) |
| T-6 | перезагрузка, затем `tmux ls` | сессия `main` существует |
| T-7 | `tmux attach -t main`, `Ctrl+A d`, `tmux ls` | отключение не убивает сессию |

## 7. Откат

```bash
systemctl --user disable --now tmux-main.service
rm -f ~/.config/systemd/user/tmux-main.service
systemctl --user daemon-reload
sudo loginctl disable-linger "$USER"
sed -i '/# tmux-autostart/,+3d' ~/.bashrc     # если раздел 5 применялся
```

Пакет `tmux` при этом остаётся. Удалять его отдельной командой имеет смысл,
только если он ставился специально под эту задачу.

## Отдельно: хост с агентами набора corp-infra

Если tmux ставится на хост, где живут `opsagent` и мосты из
`corp-infra-pop-agents` (`for-humans/34-tmux-agents-mattermost.md`), действуют
четыре дополнительных правила. Они не косметические — два из них про память и
про подтверждение человеком.

1. **Порядок вложенности: tmux снаружи, лаунчер агента внутри.** Запускайте
   `corp-agent-session` в окне tmux, а не наоборот. Лаунчер создаёт фиксированную
   scope `corp-agent-session.scope` и проверяет реальную cgroup до старта CLI; при
   обратном порядке убийство scope уносит с собой весь сервер tmux со всеми
   окнами. Учтите: имя scope фиксированное, поэтому **одновременно работает
   только одна** агентская сессия — второй запуск лаунчера отклоняется по
   построению, и это не дефект.

2. **Автозапущенный через раздел 3 tmux считается памятью пользовательского
   менеджера.** На хосте с политикой памяти агента `user@<uid>.service` лежит
   внутри `corp-agent.slice` с пределом 600 МиБ и порогом 400 МиБ
   (`corp-infra-pop-agents/for-humans/10-agent-memory.md`). Пустая сессия tmux
   стоит единицы мегабайт и в этот бюджет укладывается; Claude Code или сборка,
   запущенные внутри автозапущенной сессии, — нет. Рабочие нагрузки запускайте
   через штатный лаунчер, который уводит их в свою scope.

3. **Сессии агентов автозапуском не поднимаются.** `claude-session.sh` стартует
   Claude Code с флагом `--dangerously-load-development-channels`, который
   показывает полноэкранное предупреждение и требует подтверждения человеком один
   раз за сессию. Автозапуск такой сессии из systemd означал бы либо висящий
   неподтверждённый диалог, либо обход подтверждения. В документе 34 «автозапуск
   сессий Claude без человека» прямо перечислен среди того, что остаётся
   выключенным. После перезагрузки хоста агентские сессии поднимает человек, и
   `codex-app-server.service` тоже требует `enable-linger` — из комментария в
   самом юните.

4. **tmux — это хост-тулинг, а не service unit.** Правило «compose-файл +
   backup-манифест + vhost-фрагмент» из `corp-infra-ent-infra` к нему не
   применяется: нет контейнера, нет данных для бэкапа, нет имени для публикации.
   Единственное, что подлежит бэкапу, — `~/.tmux.conf`, и то как часть конфигов
   пользователя, а не отдельным манифестом.

## Что осталось незакрытым

- `tmux-resurrect` / `tmux-continuum` не предлагаются намеренно: они тянут
  менеджер плагинов `tpm`, который клонирует код с GitHub в домашний каталог и
  обновляется вне `unattended-upgrades`. Восстанавливают они раскладку, а не
  работавшие процессы, — ради этого расширять доверенную поверхность на хосте с
  агентами не стоит. На личной машине — вопрос вкуса.
- Пробел в `corp-infra-pop-agents/for-ai-dumb/22`, шаг B-0: команда `tmux -V`
  есть, STOP-гейт написан только для Node < 20. Отсутствующий tmux инструкцию не
  останавливает и никуда не отсылает. Правится одной строкой со ссылкой на
  раздел 2 этого документа.
